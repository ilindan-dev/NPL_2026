# 4.4 Swift — удалённый мониторинг состояния системы

Клиент отправляет запрос на сервер. Сервер собирает **реальную** статистику и возвращает
отформатированный отчёт: загрузка CPU, занятая память, load average, uptime.

```
== legion | 2026-10-02 12:00:00 +0000 ==
  CPU:     [####................] 21.4%  (ядер: 16)
  Память:  [#########...........] 46.0%  (занято 7.10 из 15.40 ГБ)
  Load avg (1/5/15 мин): 0.84 0.61 0.55
  Uptime:  0 д 3 ч 12 мин
```

**Про Network.framework.** В задании указан `Network.framework`, но он существует только
на платформах Apple (macOS/iOS). Программа запускается в Linux-контейнере, поэтому сеть
сделана на **POSIX-сокетах** (`socket` / `bind` / `listen` / `accept` / `connect`). Это
системный API, поверх которого построен и сам Network.framework. Сторонние фреймворки
(SwiftNIO) не используются. Статистика читается из `/proc` ядра Linux. Контейнер видит
`/proc` хоста, поэтому цифры относятся к вашей машине.

## Запуск (порт 5004)

```bash
# терминал 1 — сервер
./run.sh 4_client_server/task_4_swift server

# терминал 2 — клиент
./run.sh 4_client_server/task_4_swift client                  # интерактивно: ALL, CPU, MEM, ...
./run.sh 4_client_server/task_4_swift client localhost ALL    # один запрос
./run.sh 4_client_server/task_4_swift client localhost watch  # живой отчёт каждые 2 с
```

Хороший трюк для демонстрации: при открытом `watch` нагрузить процессор в третьем
терминале (`yes > /dev/null`, затем Ctrl+C) и показать, как растёт CPU.

## Как устроено

**Протокол.** Клиент шлёт команду строкой (`ALL`, `CPU`, `MEM`, `LOAD`, `UPTIME`, `QUIT`).
Сервер отвечает несколькими строками, последняя — `END`, так клиент понимает, где
кончается ответ.

**Сбор статистики**
- CPU: в `/proc/stat` лежат счётчики «тиков» процессора по режимам. Берём два замера
  с интервалом 0.5 с: загрузка = `1 − Δпростоя / Δвсего`.
- Память: `/proc/meminfo`, занято = `MemTotal − MemAvailable`.
- `/proc/loadavg`, `/proc/uptime`, количество ядер — `ProcessInfo`.

**Сервер:** `socket` → `setsockopt(SO_REUSEADDR)` → `bind` → `listen` → `accept` в цикле,
на каждого клиента `Thread`. `SIGPIPE` игнорируется, чтобы запись в закрытый сокет
не убивала сервер.

**Клиент:** `socket` → `connect` → отправить команду → читать строки до `END`.
`LineReader` буферизует байты из `read()` и отдаёт по строкам.

**Мост Swift ↔ C.** `sockaddr_in` приводится к `sockaddr` через `withMemoryRebound`, порт
переводится в сетевой порядок байт через `.bigEndian`. Это обычная работа с C API из Swift.

## Шпаргалка для видео

1. *«Задача 4.4 на Swift: удалённый мониторинг системы. Network.framework есть только на Apple, а у меня Linux в Docker, поэтому сеть на POSIX-сокетах. Это системный уровень, на котором Network.framework и построен».*
2. Показать функции сбора: *«Статистика настоящая, из /proc. Загрузка CPU считается по двум замерам счётчиков с разницей полсекунды, память из meminfo».*
3. Показать `runServer`: *«Классическая схема: socket, bind, listen, accept. На каждого клиента отдельный поток. SIGPIPE игнорируем, чтобы отключение клиента не роняло сервер».*
4. Показать протокол и `LineReader`: *«Протокол текстовый: команда строкой, ответ из нескольких строк с маркером END в конце».*
5. Демо: сервер, клиент `ALL`, потом `CPU`/`MEM` интерактивно. Затем `watch` и `yes > /dev/null` в третьем терминале: *«Видно, как загрузка CPU растёт в реальном времени».*

## Возможные вопросы

- **Зачем `.bigEndian` у порта?** В сетевых структурах числа хранятся в сетевом порядке байт (big-endian), а x86 — little-endian.
- **Почему отчёт приходит с задержкой ~0.5 с?** Загрузку CPU нельзя узнать по одному замеру, нужна разница счётчиков за интервал.
